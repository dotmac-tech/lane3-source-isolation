# Independent Lane 3 source-isolation App

Implementation draft. No App installation, hosting or live required-check binding exists yet. This source does not close N3, Gate0 or candidate allocation.

The service polls open main-targeting PRs in `dotmac-tech/lane3-exposure-execution` using a GitHub App, reads repository and synthetic merge trees through GitHub's API, and publishes `lane3-source-isolation` on the merge SHA. It never checks out or executes candidate source. It allows only the exact two inspected workflow blobs from launcher revision `67eb180022340eaea4a249cd49b06de5417b30c4`. This is deliberately stricter than parsing YAML: every workflow edit/addition/removal is refused, even a safe one, until an independently reviewed policy repin. Changes to non-workflow files do not supply code or policy to this service.

The policy is external to the execution repository. Before/after source-binding reads and merge-parent checks detect head/base drift; checks publish on synthetic merge SHAs so old checks cannot certify new merge trees. The live required-status rule must use strict/up-to-date checking and the measured App ID as expected source. Polling is not an atomic GitHub merge transaction: strict merge-SHA enforcement and race/sensitivity tests must be demonstrated before reliance. Success is source evaluation only, not full topology admission.

Dependencies: Python3.12+, system OpenSSL and HTTPS trust roots. No third-party Python dependencies, YAML parser, shell execution, webhook ingress, Docker, target/OpenBao access or database. OpenSSL signs App JWTs with a systemd-projected PEM; JWT/access tokens stay in process memory and stdout logs only outcome counts. Each bounded polling cycle obtains a target-repository-scoped installation token and attempts revocation; API failures never produce success. A token-create transport ambiguity may leave an installation token until GitHub expiry; no permanent token is minted. Current prototype creates new check runs per polling cycle; rate/cost and daemon liveness require deployment measurement.

Run synthetic tests only in the GitHub-hosted workflow. Tests include positive unchanged source, combined trigger/policy edits, indirection, missing/added workflows, oversized/truncated trees, wrong identity/merge parents and pre/post-publication drift. They do not prove live App identity binding, GitHub's merge gating or administrator separation.

## Activation packet

1. Contract owners accept the checker ownership and policy-service deployment host. A separate Proxmox VM is recommended; using Observe/seabone retains common administrative/custody trust. No host is selected or provisioned by this source.
2. Register an organization-owned private GitHub App with only Contents read, Metadata read, Pull requests read and Checks write. Disable webhooks and user authorization: outbound polling needs neither. Install for only the execution repository. Measure App ID, installation ID and permission metadata. Registration/installation requires the authenticated organization owner route; no reusable existing App was found.
3. Store the new PEM only on the approved service host at `/etc/lane3-source-isolation/github-app.pem` (root-owned0600); never in Git, terminal history, tool output or execution-repository secrets. App key custody/backup/rotation owner must be named. No OpenBao or unseal keys are needed.
4. Deploy an immutable, independently reviewed, all-green source commit under root-owned `/opt/lane3-source-isolation`. Configure root-owned `/etc/lane3-source-isolation/config` with GITHUB_APP_ID, GITHUB_INSTALLATION_ID, IMPLEMENTATION_REVISION (full deployed commit) and POLICY_SHA256 (canonical policy digest). These are metadata, not credentials. Install the provided sandboxed systemd unit. Host binaries/runtime and outbound DNS/HTTPS need validation; service network isolation must forbid private control targets. Do not expose an inbound listener or grant host/root credentials to the dynamic service user.
5. Run safe disposable PR evidence before enforcement; verify publisher App ID and merge SHA, policy/implementation binding and safe success. Then add a new required context `lane3-source-isolation` bound to the actual App `integration_id` in existing active main ruleset24557642, retaining every current rule/context, strict up-to-date behavior and no bypass. Do not use a generic unbound status or the shared GitHub Actions App as independence.
6. Live negative cases: trigger-only and combined trigger/guard/source-policy changes; a same-name check from another publisher; no checker; stale head/base; unrecognized workflow path/format; API/worker failure. Verify each is blocked from merge. Demonstrate a safe unchanged workflow tree can merge through normal review. Keep the privileged runner group empty and source workflow unchanged throughout these probes.
7. Re-read source/ruleset/App permissions/installation/host service. Record exact canonical evidence and the residual administrators who can change policy/App/rules. CP#237 and Starter#780 remain draft until owner/Michael acceptance. Their full structural dossier, credential/admission gates and admission_evidence null are unchanged.

App governance must be independent of the execution-repository PR. Protect this policy repository with its own enforced review rules before accepting its deployment; sharing an administrator is still a residual. A PR self-changing this project's tests is not independently accepted deployment code.

## Recovery

If the checker is unavailable, merges remain blocked once its required rule is active. Repair forward or use an explicitly reviewed emergency ruleset change; never silently remove expected-source binding. Stop the service and revoke the App installation/key to retire it, with a separately reviewed replacement for its required status rule. A policy repin invalidates structural evidence and requires owner review plus live revalidation.
